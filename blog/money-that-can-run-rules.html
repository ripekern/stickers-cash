Money that can run rules

Bitcoin Cash is not just a payment rail. Every coin is locked by a small program. Programmability starts with that fact — and it changes what money can do.

Post 21 of 30 · 3 min read · Oct 22, 2026

Every Bitcoin Cash transaction is already a small program. When you pay someone, your wallet does not send a file or update an account. It creates a transaction that spends coins locked by a script and creates new coins locked by another script. The network checks the script and either accepts the result or rejects it.

That is the foundation of programmability. BCH is not a payment rail with a separate smart contract platform bolted on top. The payment layer is the contract layer. The question is how much logic the network will enforce, and how cleanly that logic can be written.

Coins carry their own rules

BCH uses an unspent transaction output model. Each coin is an output with a locking script. To spend it, you provide an unlocking script that satisfies the lock. A normal payment uses a simple lock: “this can be spent by whoever can sign with the key behind this address.”

A contract uses a more interesting lock. It might say: “this can be spent only if two of these three keys sign,” or “only after this date,” or “only if the money goes back to this address,” or “only if the transaction also moves this token.” The rule travels with the coin. There is no central account that has to approve it.

This is the key mental shift. On an account-based smart contract chain, a contract has a persistent balance and a global state that everyone reads and writes. On BCH, a contract is a lock on a set of coins. Its “state” lives in the outputs it controls, in the tokens attached to them, or in data committed inside an NFT. Spending the coins is how you update the state.

Local rules, global reach

That difference is not a detail. It changes how applications are designed. A BCH contract does not need every node to execute a shared application state for every user. It validates a transaction locally: do the inputs satisfy the locks, and do the outputs follow the rules? If yes, the transaction is valid.

This is why BCH contracts can be cheap and parallel-friendly. There is no global contract storage to synchronize and no separate gas token to buy. The fee is paid in BCH, and it is based on transaction size, not on how many computational steps a global virtual machine performed.

BCH is focused on money, assets, and settlement. That focus is the advantage: contracts are small, validation is local, and fees stay predictable. You get the rules you need for payments without the overhead of a global general-purpose computer.

The toolbox has been growing

For years, BCH Script could already do multisig, timelocks, hashes, and conditional payments. Then the toolbox expanded quickly:

  • 2022: native introspection, which enabled covenants — contracts that can inspect the transaction spending them.
  • 2023: CashTokens, adding native fungible tokens and NFTs to the same chain.
  • 2025: reworked VM limits and arbitrary-precision integers, removing artificial ceilings on more advanced contracts.
  • 2026: bounded loops, reusable functions, bitwise operations, and standard pay-to-script outputs — more expressive contracts without a separate VM.

BCH does not need to be Ethereum. It is becoming a better version of itself: money that can enforce useful rules, with the same cheap settlement and self-custody that made it interesting in the first place.

The rest of this chapter is about what those rules can actually do. We start with the script that sits under every wallet, then move up to the languages and primitives built on top of it.
