BCH NFTs in Detail

Category, commitment, capability, and how BCH NFTs work as verifiable claims on the blockchain.

This deep dive expands on the NFT layer mentioned in "NFTs with the receipt built in." It covers the technical structure of BCH NFTs, how they differ from other chains, and how they work as verifiable claims. This is technical content for developers and the deeply curious.

The three properties

Every BCH NFT has three properties encoded in the UTXO that holds it:

  • Category: A 32-byte identifier that ties the NFT to its token family. The category is derived from the transaction that created the NFT (the outpoint of the minting transaction). All NFTs in the same category share the same issuer and metadata registry.
  • Commitment: A piece of data embedded in the NFT. Before 2026, commitments were limited to 40 bytes. After the May 2026 upgrade, the limit is 128 bytes. The commitment can hold a hash, a timestamp, an identifier, a score, a ticket number, or any compact piece of state that a contract needs to verify.
  • Capability: A single byte that controls what can be done with the NFT. There are three capabilities: minting (0x01), mutable (0x02), and immutable (0x00).

Capabilities in detail

The capability field is what makes BCH NFTs flexible:

  • Minting NFT (0x01): Can create new NFTs in the same category. A minting NFT is like a master key — its holder can issue unlimited NFTs with new commitments. This is useful for ticketing systems, membership programs, or any use case where the issuer needs to create many unique tokens over time.
  • Mutable NFT (0x02): Can update its own commitment when spent. A mutable NFT can change its data payload, making it useful for state that evolves: a game item's stats, a membership tier, a timestamp, or a contract's current value. The NFT remains the same identity, but its claim can be updated by its owner.
  • Immutable NFT (0x00): Cannot change once created. An immutable NFT is permanent — its commitment is fixed forever. This is ideal for certificates, receipts, credentials, or any claim that should never be altered. Once issued, the claim is set in stone (or rather, in consensus rules).

The 2026 upgrade

The May 2026 upgrade raised the standard commitment limit from 40 bytes to 128 bytes. This tripled the amount of data an NFT can carry on-chain. The upgrade also made bare pay-to-script outputs standard, which simplifies contract construction.

What fits in 128 bytes?

  • A SHA-256 hash (32 bytes) — enough to commit to a document, a file, or a dataset
  • A timestamp (8 bytes) plus an identifier (up to 120 bytes)
  • A ticket number, seat, section, and event ID
  • A compact state record: a counter, a status flag, and a reference hash
  • A small JSON-like structure (if encoded efficiently)

This is enough for most real-world use cases. You don't need to store large files on-chain. You need to store a claim — a hash, an identifier, a piece of state — and the network enforces that claim.

How contracts use NFTs

A BCH contract (script) can inspect an NFT's category and commitment. This is what makes NFTs useful in programmable money:

  • Gate contracts: A contract can require that the spender present an NFT with a specific category and commitment. For example, a "members-only" vault might require an NFT with the membership category and a commitment showing the membership is active and not expired.
  • Redemption contracts: An NFT can act as a receipt. Return the NFT to the contract, and the contract releases the underlying asset. This is useful for tickets (redeem for entry), vouchers (redeem for goods), or bonds (redeem for principal).
  • Role-based contracts: An NFT can act as an admin key. A contract checks for the NFT before allowing a privileged action (e.g., changing parameters, withdrawing funds, or minting more tokens).
  • State contracts: A mutable NFT can hold the latest state of a contract. When the contract is updated, the NFT's commitment is updated to reflect the new state. The NFT becomes a portable, verifiable record of the contract's current value.

Metadata at the edges

BCH NFTs are minimalist by design. The on-chain data is small: category, commitment, capability. Rich metadata — names, descriptions, images, animations — lives off-chain in Bitcoin Cash Metadata Registries (BCMR).

BCMR is a standard for publishing authenticated metadata. A token issuer registers their NFT collection's name, description, icon, and other details in a BCMR registry. Wallets and explorers fetch the metadata and display it alongside the on-chain data. The result is a compact on-chain primitive with rich presentation around it.

Why separate the metadata from the chain?

  • Cost: Storing images or large text on-chain is expensive. Off-chain storage is cheap or free.
  • Flexibility: Metadata can be updated (e.g., fixing a typo, adding a new image) without modifying the blockchain.
  • Efficiency: The chain validates the token; the registry provides the presentation. This separation of concerns keeps the chain lean.

The trade-off is that you need to trust the metadata registry (or run your own). But the on-chain token data — category, commitment, capability — is immutable and verifiable by every full node. The metadata is presentation; the token is the truth.

Comparison with other chains

BCH NFTs are fundamentally different from NFTs on Ethereum, Solana, or other chains:

  • Not a link to a file: Most NFTs on other chains are just tokens that point to a URL (usually an IPFS hash or an HTTP link). The token itself has no inherent meaning — it's just a pointer. BCH NFTs carry a commitment on-chain, which is verifiable by the network.
  • Native, not an afterthought: CashTokens are part of the BCH consensus layer. They're validated by every full node, just like BCH. There's no separate token standard, no smart contract layer, no bridge.
  • Cheap: Minting a BCH NFT costs a fraction of a cent in normal conditions. There's no separate gas token, no auction mechanism, no layer-2 scaling solution needed.
  • Programmable: BCH NFTs can be used in contracts. They're not just collectibles — they're verifiable inputs to rules. A contract can check an NFT's category and commitment before executing logic.

Practical use cases

What can you actually build with BCH NFTs?

  • Tickets: Each ticket is an NFT with a commitment containing the event ID, seat, and section. The gate contract checks the NFT before allowing entry. The ticket can't be counterfeited because the commitment is on-chain.
  • Receipts: A purchase generates an NFT with a commitment containing the order hash. The customer can return the NFT to claim a refund, warranty, or return. The receipt is verifiable and can't be forged.
  • Memberships: A membership program issues NFTs with a commitment containing the membership tier and expiry date. The member presents the NFT to access member-only content, discounts, or events. The membership can be updated (mutable NFT) or locked (immutable NFT).
  • Game items: In-game items are NFTs with commitments containing stats, rarity, or ownership history. The game contract checks the NFT before allowing the item to be used. The item can be traded, upgraded (mutable), or locked (immutable).
  • Credentials: A credential (degree, certification, license) is an immutable NFT with a commitment containing the credential hash. The holder presents the NFT to prove the credential. The credential can't be altered or forged.
  • Loyalty points: A loyalty program issues fungible tokens (points) and NFTs (badges, achievements). The tokens are divisible and interchangeable; the NFTs are unique and verifiable.

Why this matters

BCH NFTs are not about digital art or speculation. They're about verifiable claims. An NFT is a compact, checkable token that proves something: a ticket is valid, a receipt is authentic, a membership is active, a credential is real.

The NFT is not the product. It's the proof that the product's rule was followed. The product might be a ticket, a receipt, a membership, a game item, or a credential. The NFT is the verifiable, on-chain anchor that makes the product trustworthy.

That's the BCH pattern: keep the core small, but make the core enforce the things people actually need. NFTs are useful. Making them native makes them cheaper, safer, and easier for contracts to use.
